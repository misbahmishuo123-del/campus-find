# CampusFind — University Lost & Found

CampusFind is a university Lost & Found system built as a **Flutter mobile app** that talks to a **Node.js + Express + TypeScript REST API** backed by **MongoDB Atlas**.

Students and staff can report lost and found items, search, see ranked *possible matches*, submit claims with a hidden verification answer, and track everything through in-app notifications. University security/admin staff review claims, verify ownership, approve or reject them, and mark items as returned.

> **Important principle:** a match is only ever a *possible* match. The system never declares ownership automatically — the final decision always requires human verification by authorized staff/admin.

---

## 1. Architecture

```
Flutter (mobile app)
        |  HTTPS / REST  (Bearer JWT)
        v
Node.js + Express + TypeScript  (API layer, auth, matching, rules)
        |  Mongoose ODM
        v
MongoDB Atlas  (users, items, claims, notifications, auditLogs)
```

- The Flutter app **never** connects to MongoDB directly and holds **no secrets**.
- All passwords are hashed with **bcrypt**; authentication uses **JWT**.
- Optional Gemini AI is only ever called from the backend and the core workflow does **not** depend on it.

## 4. Installation

### Prerequisites
- Node.js 18+ and npm
- Flutter SDK 3.x (with `flutter doctor` passing) and Dart
- A MongoDB Atlas cluster

### Backend
```bash
cd backend
npm install
```

### Frontend
The Flutter platform folders (android/, ios/, etc.) are generated by Flutter itself.
Run this once inside the app folder — it fills in the missing platform scaffolding
without touching the existing `lib/` code or `pubspec.yaml`:
```bash
cd frontend/campus_find
flutter create . --platforms=android,ios
flutter pub get
```

## 5. Environment variables

Create `backend/.env` (a ready `.env.example` is provided). **Never commit `.env`.**

```
PORT=5000
MONGODB_URI=YOUR_MONGODB_CONNECTION_STRING
JWT_SECRET=YOUR_JWT_SECRET
GEMINI_API_KEY=YOUR_GEMINI_API_KEY      # optional
UNIVERSITY_EMAIL_DOMAIN=                # optional, e.g. university.edu
```

- `MONGODB_URI` — your Atlas SRV connection string.
- `JWT_SECRET` — a long random string used to sign tokens.
- `GEMINI_API_KEY` — optional; the app works fully without it.
- `UNIVERSITY_EMAIL_DOMAIN` — if set, student/staff registration emails must end with `@your-domain`. Leave empty to allow any valid email.

No secret is ever placed in Dart files, Flutter config, the README, or git.

## 6. MongoDB Atlas setup

1. Create a free cluster at mongodb.com/cloud/atlas.
2. Create a database user (username + password).
3. Under **Network Access**, allow your IP (or `0.0.0.0/0` for a quick demo).
4. Click **Connect → Drivers** and copy the SRV string into `MONGODB_URI`.
5. The database and collections are created automatically on first write.

Collections used: `users`, `items`, `claims`, `notifications`, `auditlogs`.

## 8. Flutter startup

First, tell the app where the backend is. The base URL is **not** a secret and is
supplied at run time via `--dart-define` (default in `lib/core/constants.dart` is
`http://10.0.2.2:5000/api`, which is how the **Android emulator** reaches your
computer's `localhost`).

```bash
cd frontend/campus_find

# Android emulator (backend on your machine's localhost:5000)
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:5000/api

# iOS simulator / desktop
flutter run --dart-define=API_BASE_URL=http://localhost:5000/api

# A physical device on the same Wi-Fi (use your computer's LAN IP)
flutter run --dart-define=API_BASE_URL=http://192.168.x.x:5000/api
```

## 9. API overview

Base path: `/api`

**Health**
- `GET /health`

**Auth**
- `POST /auth/register` — `{ name, email, password, role }` (role is only `student`/`staff`; admin is created out-of-band)
- `POST /auth/login` — `{ email, password }` → `{ token, user }`
- `GET /auth/me` — current user (Bearer token required)

**Items** (all require Bearer token)
- `POST /items` — report a lost/found item (optional `verificationQuestion` + `verificationAnswer`)
- `GET /items?type=&category=&location=&color=&brand=&status=&q=&page=&limit=` — search & filter
- `GET /items/:id` — item details
- `GET /items/:id/matches` — ranked possible matches with score breakdown
- `PATCH /items/:id` — edit (owner or admin)
- `DELETE /items/:id` — delete (owner or admin)
- `GET /my-reports` — the current user's items

**Claims**
- `POST /items/:id/claim` — `{ reason, verificationAnswer }` (cannot claim your own item)
- `GET /my-claims` — the current user's claims

**Notifications**
- `GET /notifications`, `PATCH /notifications/:id/read`, `PATCH /notifications/read-all`

**Admin** (role = `admin`)
- `GET /admin/stats`
- `GET /admin/claims?status=`
- `GET /admin/claims/:claimId` — full detail incl. verification match + possible matches
- `PATCH /admin/claims/:claimId` — `{ status: "approved"|"rejected", adminNotes }`
- `PATCH /admin/items/:id/return` — mark an item returned

## 10. User roles

| Role | Can do |
|------|--------|
| **student / staff** | Report lost & found, search, view possible matches, submit claims, view own reports/claims, receive notifications |
| **admin (security)** | Everything above (review) plus: view all claims, verify & approve/reject claims, mark items returned, view dashboard statistics |

Roles are enforced **only** on the backend from the signed JWT. A role sent from the client is never trusted — self-registration as `admin` is impossible.

---

## 11. Main workflow

```
LOST  →  FOUND  →  POSSIBLE MATCH  →  CLAIM  →  ADMIN VERIFICATION  →  RETURNED
```

1. A student reports a **lost** item.
2. Someone reports a **found** item (optionally with a secret verification question/answer).
3. The backend ranks **possible matches** on a 100-point scale:
   - Category 25 · Location 25 · Date/time 20 · Description 20 · Color/brand 10
   - 80–100 Strong possible match · 60–79 Possible match · 40–59 Weak match · 0–39 None
4. The owner submits a **claim** with a reason and their verification answer (compared against the hashed secret).
5. **Admin/security** reviews the claim, sees whether the secret answer matched plus other possible matches, then **approves** or **rejects** it.
6. On approval the item becomes `verified`; the admin can then **mark it returned**.
7. Notifications and audit-log entries are created at each step.

Verification answers are stored **hashed** (bcrypt) and are never returned by any API — not even to admins (admins only see whether the answer matched).

---

## 12. Security notes

- bcrypt password hashing, JWT auth, role-based authorization.
- Input validation and protected routes.
- CORS enabled; environment variables for all configuration.
- No secrets in the frontend, no plaintext passwords, no secret answers in public responses.

## 13. Demo instructions

Seed the database with a demo admin, two students, and sample items:
```bash
cd backend
npm run seed
```

**DEVELOPMENT-ONLY** demo logins (not real secrets — change them for production):
```
admin    → admin@campusfind.edu / Admin@123
student  → sara@student.campusfind.edu / Student@123
student  → ali@student.campusfind.edu  / Student@123
```

Suggested demo flow:
1. Log in as **sara** → open the lost wallet → *View possible matches* (see the found wallet ranked).
2. Log in as **ali** (or register) → open the found wallet → *Claim this item*.
3. Log in as **admin** → *Review claims* → open the claim → **Approve** → **Mark item as returned**.
4. Log back in as the owner and check **Notifications**.

Run the automated end-to-end workflow test (backend must be running):
```bash
cd backend
node scripts/e2e.mjs
```
